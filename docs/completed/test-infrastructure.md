- Feedback in der CI (17. bis 21.11.2026; Commits 88a934eb und 9714eb85, Schritt der Spur M): Ab 17.11. las devbox die Page-Fault-Kosten seines Hosts 7- bis 10-mal höher, und ein Feedback-Spiel lief über die Grenze des Harness (der Lauf vom 19.11.: 573756 erreichte die 2.100 s, 562428 brauchte 10,7 Minuten statt 1,2). `scripts/feedback-ci.mjs --name <name> [--runs 3]` weigert sich bei einem schmutzigen Baum, pusht den einen Zweig `feedback/<name>` (den gemessenen Commit plus `.feedback-run.json`) über die URL des Repositorys, und `.github/workflows/feedback.yml` fährt N ganze Feedback-Läufe, je einen auf einem Runner mit `FEEDBACK_DUMP=1`, einem Playwright-Worker und ohne Trace. Das Skript wartet im Vordergrund, lädt die Artefakte nach `.calibration/feedback-<name>/run<i>/`, vergleicht sie mit demselben Modul noch einmal, druckt die Wandzeit jedes Jobs und löscht den Zweig; `--reuse` findet einen geladenen Lauf desselben Commits. Der Harness liest nur verfolgte Fixtures, ein Lauf braucht also keinen Datendownload. `feedback-ci.spec.ts` und `feedback-workflow.spec.ts` halten die Sicherheitseigenschaften des Workflows (nur ein Push auf `feedback/**` oder ein Lauf von Hand startet ihn, das Token liest nur das Repository, jede Action ist von GitHub und auf einen Commit festgelegt), die Dateiliste des Vergleichs gegen den Harness und die Pushes des Skripts. Das stehende Okay des Users (20.11.) deckt Push und Löschen der `feedback/<name>`-Zweige; AGENTS.md, README, ARCHITECTURE und EVALUATION nennen das Skript. Lehre: Eine Maschine, deren Kosten sich ohne Änderung der Software um den Faktor 7 bis 10 verschieben, braucht eine zweite, auf der dasselbe Skript läuft; ein langsamer Lauf wird zuerst Basis gegen Kopf auf einem Spiel verglichen, bevor man den Code verdächtigt.
