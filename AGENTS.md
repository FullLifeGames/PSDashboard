# AGENTS.md

Rules for agents working on PS Dashboard. Claude Code reads this file through `CLAUDE.md`. Every open task is a GitHub issue (`gh issue list`): the milestones name the releases, and the project board "PS Dashboard" carries the wave in hand (`gh project item-list`); finished rounds are in `docs/completed/`. Name the project's concepts with the words of `GLOSSARY.md`; before you change a decision that `docs/adr/` records, read its ADR.

## The project

PS Dashboard analyzes Pokémon Showdown replays: it replays a game turn by turn, branches at any turn ("what if"), and grades moves with its own evaluation engine.

- `src/`: the React app (Vite, TypeScript), published on GitHub Pages.
- `packages/replay-core` (`@fulllifegames/replay-core`): parser, snapshots, team building, spread solver.
- `packages/eval-engine` (`@fulllifegames/eval-engine`): static evaluation, MCTS trees, verify round, prover, report.
- `test/regression/`: Node tests of the app and the calibration bank (`eval-calibration.spec.ts`, which also holds the ledger of every round); `test/ui/`: component and hook specs under jsdom; `test/e2e/`, `test/e2e-capture/` (the capture of saved engine results, `scripts/capture-eval-store.mjs`) and `test/e2e-build/`: Playwright; `test/e2e-feedback/`: the feedback corpus with the expert pins (`corpus.ts`). Each package keeps its specs in its own `test/`.
- Keep the three layers apart: ingestion and inference, deterministic reconstruction with `@pkmn/sim`, user interface.
- Branches: since the release of 1.1.0 the work lands on `master` (user gate 07.11.2026; `dev` carried it from 1.0.0 to 1.1.0). Each round, lane or batch runs on its own branch from `master` and reaches master through a pull request; master requires the PR and the nine required checks of `test.yml` (listed under "Checks before commit and push"), for admins too, and the branch is deleted after the merge. A merge into master updates the nightly at the root of GitHub Pages once its Tests run passes (`pages.yml` waits for `test.yml`). A release is the commit that raises the version (`npm version <minor|patch> --workspaces --include-workspace-root --no-git-tag-version`): `release.yml` finds a version without a tag and makes the tag, the GitHub Release, the npm packages and the frozen copy; the last one is v1.2.0 (tag `v1.2.0`, 22.11.2026). The production copy on fulllifegames.com, which the README calls the release, changes only through the local `deploy.ps1`, run after the release's push (1.0.0 to 1.2.0).

## Working with the user

- Plain language: every summary, gate and report starts with the problem in one game scene, the idea with an everyday comparison, what changes for the user, and how success is measured. Project terms (pin, gate, golden, bank) are fine; new coinages are not.
- Gates: numbered questions in plain text, two sentences of scene per question, options a/b/c in one or two sentences each, the recommendation marked, answer format "1a 2a 3a".
- Gate questions reach the user as a review page (user 13.11.2026): a private Artifact that holds only the questions still open, one card per question (the scene, the options, the recommendation marked, a note field, the screenshots and mocks the question rests on). The page stores each answer (`db` capability, one document per question under `answers/<id>` with `choice`, `note`, `at`) and shows the answer line with a copy button as a fallback. Every version of the page ends with one free-text field below the last question (user 20.11.2026), stored as `answers/_free` with `note` and `at`, for feedback that fits no question. The integrator reads it with the answers and treats each point as a report: a small fix with a known cause gets built, and the rest returns as a question with a recommendation. The chat carries the link and one line on what is open. After the user says the page is filled, read the answers from its store, record them as a ruling in the round's brief, and publish the next version with the questions that remain.
- Tracked documents and every user-facing string go through the `stop-slop` skill: no dashes as separators, no filler adverbs, active voice, specific claims. Exceptions: verbatim quotes of app output, technical invariants with "never" or "always", placeholder glyphs. The engine's prose (`summary.ts`, `report.ts`) is pinned by the feedback corpus: a change to it moves pins, and they wait for the gate of its round or batch.
- Commits: English, imperative, release style, no attribution lines (no Co-Authored-By). Write messages with quotes to a file and use `git commit -F <file>`.
- A pull request says first what it produces (user 22.11.2026): the title names the release or the change, and the body opens with a Summary of one or two sentences (the version it ships, the count of commits and issues) and a short sketch with `+` for a new feature, `~` for changed behaviour and `-` for what goes away. Then come "New features", "Changes to existing behaviour" and "Fixes" (grouped by area), each item with its issue number, then "Packages" and "Tests and tooling" where they move. "Evidence" is one table of check and result, "Merge Danger" names the door (one-way or two-way) and what a user notices after the merge, and "Closes" lists the issues on one line, with the ones that close with a rest below it. The full measurement record stays in `docs/completed/` and the ledger; the body points there. Check every feature claim against the issue and the code: new or renamed, and which version a format carries.
- No merge into master, and no deleting branches, worktrees or files you did not create, without the user's okay. An okay covers the named state only. Pushing a round, lane or batch branch and opening its pull request is covered by the user's standing okay (07.11.2026), and so is pushing and deleting `bank/<name>` and `feedback/<name>` branches (user 13.10.2026 and 20.11.2026); merging a pull request is the user's okay for that state. A release (the pull request that raises the version) and `deploy.ps1` each need an okay of their own that names the release (user 29.10.2026 and 07.11.2026).
- The user reports library bugs upstream himself; collect them as an upstream list with a scene and evidence.
- Re-pins (a test or pin whose expected verdict changes) happen only at the user gate.

## Rules for the code

- Game rules come from the simulator and the Dex (`@pkmn/sim`, `@pkmn/dex`, `@pkmn/mods`, `@pkmn/client`, `@pkmn/protocol`). Our code translates and reads library data, never species or move names. Where our code must know a rule, a test checks it against the simulator. Moving logic into the libraries is welcome.
- Every rule comes from the game's own Dex: the battle's `battle.dex`, else the resolver of generation and mod (`rulesDex` in `replay-core/src/rules-dex.ts`). The code of replay-core, eval-engine and the app reads the global Dex (Generation 9 without a mod) nowhere else, and the lint rule `dex/no-global-dex-read` holds it; specs read it as the oracle. Every realm that rebuilds a game (the main thread, a worker, a Node harness) loads the Champions mod itself before it asks the resolver (user 23.10.2026; round 75: the app's replay worker did not).
- A fix for a game rule starts with a sweep: a test that plays every Dex entry of that kind, in every generation and mod the corpus plays, and compares the simulator with our reading; the reported scene becomes one row of it (models: `pair-stall-guard.spec.ts`, `power-handlers-census.spec.ts`). A list in a hot path may stay while such a test holds it to the Dex.
- One rule lives in one module, and every other place imports it. A deliberate copy (a package that reaches the other only through its barrel) gets a spec that compares the two.
- A question to the simulator runs on a copy of the battle. A stand-in that calls a Dex handler gets a sweep over every Dex entry that can reach it, and the sweep proves the live battle unchanged (`fingerprint` in `packages/eval-engine/test/power-oracle.ts`).
- A rule that is right by the game stays, even when the bank reads it worse: then the weights are wrong, and a refit becomes a TODO. Published Smogon sets are read as published.
- Pokémon Champions and Scarlet/Violet differ in rules: that is a question of the battle's mode, not a bug.
- A Custom Game (draft leagues) plays with each species' own abilities; only Hackmons formats are free. Before recommending anything that rests on a game rule, check that the species can really have it.
- PP and heal fractions come live from the simulator (`moveSlots[].pp`, `move.heal`), never derived from Dex base values.
- Singles and doubles are equal citizens, and VGC (Scarlet/Violet and Champions) counts on its own: every feature covers both game types in the same step, every measurement counts doubles and VGC separately.
- Comments: a comment stays only when deleting it loses a fact that the code, its names and its types do not give: a game rule with its source (the Dex entry, the simulator handler, the protocol line), an invariant the code relies on and does not check, a trap with the scene that showed it, or the unit or contract of a public field. A comment never retells the code and never carries history (rounds, rulings, dates, T-numbers, issue numbers, "since", "before", "today"); history lives in `docs/completed/` and the commit log. A design across modules lives in ARCHITECTURE.md (layers, data flow), EVALUATION.md (scoring, search, prover), ENGINES.md (the engine protocol), an ADR (a decision and its reasons) or the package README (how to call it), and the code names it in one line at most. A file header is one sentence. Each package export keeps one line of JSDoc, its hover text; a member keeps JSDoc only for a unit or a contract. Tests follow the rule and may name their game scene. Comments that code reads stay as they are: the `// oracle:` markers (they name the spec that holds the list; one spec still reads its own), `eslint-disable` lines, `@ts-expect-error`, `@vitest-environment`, coverage pragmas, `/// <reference`, shebangs and legal headers. `comments/no-history` (`eslint.comments.mjs`) holds the history patterns per file against `comment-ratchet.json`, and the same file holds the comment lines per project (`node scripts/comment-counts.mjs`, run by `npm run lint`); both only fall, `node scripts/update-lint-ratchet.mjs` lowers them. A clean-up edit of comments proves that no code moved with `node scripts/comment-only-diff.mjs <base> [--head <rev>] [paths]`: exit 0 when every changed file differs only in comments and whitespace and the code-read comments are byte for byte the same.
- React: state that follows a prop is reconciled during render, never in an effect (lint rule `react-hooks/set-state-in-effect`).
- Formats that leave the app carry a version: the engine protocol (`ENGINE_PROTOCOL` in `packages/eval-engine/src/engine-api/protocol.ts`), the state file of `Report issue` (`SUPPORT_STATE_VERSION` in `src/lib/support-state.ts`) and the shared-branch link (`version` in `src/lib/branch-share.ts`). A change that breaks a reader on the other side raises the version, and the app keeps reading the old one; a new optional field keeps it (round 77: the names in share links).
- Dependencies: direct dependencies track their latest registry versions (`npm outdated`). Three exceptions: TypeScript stays on 6.x until typescript-eslint admits the 7.x compiler, `@types/node` follows the Node major the workflows run, and `@pkmn/sim` and `@pkmn/mods` stay pinned to one exact version in every manifest, because the speed layer copies the simulator's classes and checks no hash in the browser (`test/regression/pkmn-pins.spec.ts`). `npm run upgrade:pkmn [version]` moves the whole @pkmn release train (sim, mods, dex, data) at once and prints the checks a new simulator needs before it ships (T103, the engine suite in all speed-layer modes, the batch check).

## Checks before commit and push

- `npx tsc -b` (`tsc --noEmit` checks nothing in this solution setup), `npm run lint` and `npx knip` before every push; CI runs `npm run knip` and `npm run lint` in the required job `Production build smoke` of `test.yml`, and the Pages workflow has its own lint gate. The lint ratchet (`eslint.ratchet.mjs`) only shrinks: split a file instead of raising its limit, and run `node scripts/update-lint-ratchet.mjs` after a refactor (it also lowers the spec-file counts, rule 5 below).
- Tests: `npx vitest run --project <eval-engine|replay-core|ui|app>` or single files; the full suite with `npx vitest run`; e2e with `npm run test:e2e` (a separate port via `PS_DEV_PORT`; CI runs the browser flows in three parts and gates them with the job `Browser flows`, and a new file in `test/e2e/` goes into the part with the least seconds in `test.yml`, which `workflows.spec.ts` checks). The dice sweeps play every move only with `DICE_SWEEPS=full`; a plain run plays a fixed sample of them. CI plays them full in the dice job (the `dice-*` specs) and in the three parts of the job `Full sweeps, the other specs` (every other spec that reads the switch; `workflows.spec.ts` holds the lists). `Node suites` runs the app, ui and replay-core projects; the engine project runs in its two jobs, speed layer forced off and forced on.
- Required checks (nine contexts, `workflows.spec.ts` lists them): `Node suites`, `Engine suite, speed layer forced off`, `Engine suite, speed layer forced on`, `Dice sweeps, every move`, `Full sweeps, the other specs, part 1 of 3`, `part 2 of 3`, `part 3 of 3`, `Browser flows`, `Production build smoke`. A job in `test.yml` that is added, renamed or split changes this list in branch protection in the same pull request.
- The final suite of a round runs in plain mode in the main checkout, for what CI cannot run: the local test data (the saved replay HTML of `reconstruction.spec.ts`, the fit corpus). A clone or a worktree skips those tests; the report lists the skipped tests (`--reporter verbose` marks them; round 74: a test that skipped in the merge clones stayed red for ten days, user 23.10.2026). The full sweeps and the engine suite with the speed layer forced off come from the pull request's required jobs; nobody sets `DICE_SWEEPS=full` or `EVAL_SIM_FAST=0` for the round's final suite.
- Package exports: a barrel change shows as a diff under `test/regression/fixtures/api/` (`UPDATE_API_SNAPSHOT=1` only on purpose), then `npm run pack:smoke`.
- Test first: a red test that fails for the right reason, then the code.

### What earns a test

1. One behaviour, one layer: the lowest layer that can show it (a pure function in its package; a game rule in a Dex sweep against the simulator; a view in a ui spec; layout, the replay iframe, the worker or a live search in a browser row). A row that reads only text or state does not belong in a browser spec. A second layer checks the seam with one row per game type.
2. A reported scene becomes a row of the sweep of its rule when one exists, else one row in the spec of its module; it gets no file of its own.
3. A fix's red test goes into the spec of the module it fixes. A new spec file needs a new source module, a new sweep or a new browser flow, and the pull request names it. File names and test names carry no round, T-number or issue number.
4. No test pins a past shape of the code (a file exists, a name is not exported, an import style, a comment). knip, lint, the twin lists and the name guards hold shape; a source scan stays only for a rule of this file that none of them can hold.
5. At most one spec file per source module beside its sweeps; a spec stays under the 600 code lines of the lint ratchet, and a module whose rows pass them splits into `<module>.<topic>.spec.ts`. The count of spec files per project only falls: `spec-count-ratchet.json` holds it, `npm run lint` checks it, `node scripts/update-lint-ratchet.mjs` lowers it after a cut, and `--allow-raise` raises it for a new module the pull request names.
6. A cut is proven: the rows by project and full name before and after (both speed modes), the coverage of the touched files before and after with no statement, branch or function lost, and for a removal a mutation that turns the surviving row red. The commit names the surviving row.
7. Never cut: the expert pins and the feedback corpus, the play-out pin (`test/e2e/branch.spec.ts`, draft t56), the golden replay 655336, rows a user gate fixed (they may move file, byte for byte), the Dex sweeps as a class with every entry in the full run, the calibration ledger, and the only row of a game type (singles, Doubles OU, VGC, Champions OU, Champions VGC).
8. Each run once: a CI job does not repeat the rows of another required job, and the round's final suite on devbox runs only what CI cannot (see the line above).

## Measuring and judging

- Score-touching changes (D3): bump the cache version once per round (`EVAL_ENGINE_CACHE_VERSION` in `src/lib/eval-cache-store.ts`), run the paired bank against a fresh base of the same day, run the feedback corpus three times byte-identical, and read the tier census (`node scripts/tier-census.mjs`, with `--moved` for every moved turn). A batch of small fixes uses its batch check instead (see Change classes).
- Bank verdicts (`scripts/paired-calibration.mjs`, tables full and hq, fixed K and own K per phase): pooled rows decide, phase cells warn. Harm means a pooled row at least 5 bp worse with its band wholly on the bad side; a warning is the same in a phase cell.
- Doubles verdicts read the bank together with the Doubles OU and VGC holdouts (D26); the Champions families have their own holdouts.
- A holdout that reads harm in a pooled row the fit side does not repeat gets a fresh draw of its family before any refit (user 06.11.2026; round 86: the VGC holdout, in service since round 65, read the wave with the hashed tree seeds as harm, 1,245 fresh games read it better, and `holdout-vgc2` replaced it). `scripts/fresh-holdout.mjs` draws VGC families; the other families need T342 first.
- The bank guards against harm and does not prove a gain (user 22.10.2026). Dice and player errors make game outcomes noisy, so effects of a few bp rarely resolve (T52, T224 and T163 adopted nothing). The game's rules and the expert pins decide a feature or a rule fix; the bank and the holdouts check it for harm. A re-fit of a weight or a K runs only where the bank reads harm after a game-correct change, never to look for a gain.
- Lossless changes (D4): three byte-identical feedback runs, the bank digit-identical, regression, e2e, lint, `tsc -b`.
- Order for tree and verify changes: the play-out pin first (`test/e2e/branch.spec.ts`, draft t56), then the golden replay 655336, then the bank.
- Set and solver changes: set diffs on every build path before the bank (the bank builds like the app, through `buildAppTeams`).
- Monte-Carlo references of scene pins price their leaves with the engine's static evaluation: recompute them after every weight change before calling a pin wrong.
- Wall-clock timing only interleaved with the base on a quiet machine, both sides in one worktree that checks them out in turn (round 72: two checkouts of one commit read up to 2 % apart); no tests, probes or agents meanwhile. The feedback harness reads a test's duration in steps of about ten seconds (round 79), so the cost of a sweep needs a Node probe.
- Feedback dumps (`feedback-full-*.json`) exist only with `FEEDBACK_DUMP=1`; check their mtime before reading them.

## Tools and pitfalls

- Bank in CI (round 71, the default): `node scripts/bank-ci.mjs --name <name>`; a holdout adds `--env EVAL_CALIBRATION_SOURCE=holdout --tranche holdout-<doublesou|vgc2|championsou|championsvgc>` (round 86: `holdout-vgc2`, 1,410 fresh games, replaced the spent `holdout-vgc` as the VGC judge, ADR 0006), the quick tier `--env EVAL_CALIBRATION_FRACTION=0.25`. The script pushes the one branch `bank/<name>` (the measured commit plus `.bank-run.json`), `.github/workflows/bank.yml` runs 16 jobs of 4 slices, and the script downloads the merged run into `.calibration/<name>/` and deletes the branch. The user's standing okay covers pushing and deleting `bank/<name>` branches (and, since 07.11.2026, pushing round, lane and batch branches and opening their pull requests). A bank run takes about five minutes there when it runs alone, the four holdouts with the old VGC holdout took about 25 together, and `holdout-vgc2` alone took 38 (round 86), and CI rows are byte-identical to local rows of the same engine (bank 837 of 837, VGC holdout 1,121 of 1,121 in round 71), so a CI run pairs with a local base and the other way round. CI measures only commits that carry this tooling. CI runs have no slice limit and run side by side, but `bank-ci.mjs` writes to `.git` when it pushes and deletes, so it does not start while a local heavy run is going; `bank-ci.mjs --reuse` finds a downloaded run of the same commit and settings.
- Feedback in CI (round 89, user 20.11.2026): `node scripts/feedback-ci.mjs --name <name> [--runs 3]`. From 17.11.2026 devbox read the page-fault cost of its host 7 to 10 times higher, and a feedback game passed the harness cap there. The script refuses a dirty tree, pushes the one branch `feedback/<name>` (the measured commit plus `.feedback-run.json`) by the repository's URL, and `.github/workflows/feedback.yml` runs N whole feedback runs (default 3), each on its own runner with `FEEDBACK_DUMP=1`, one Playwright worker and no trace. Every run uploads its dumps (`feedback-full-*.json`), its drift report and its log as the artifact `feedback-run-<i>`; a last job compares the dumps of all runs byte for byte and the drift reports without their date and wall times. The script waits in the foreground, downloads the artifacts into `.calibration/feedback-<name>/run<i>/`, prints the wall time of every job and the compare job's verdict, compares the downloaded files again with the same module, and deletes the branch. `--reuse` finds a downloaded run of the same commit and run count. The harness reads only tracked fixtures, so a run needs no data download. Like the bank, the script writes to `.git` when it pushes and deletes, so it does not start while a local heavy run is going.
- Bank locally: `node scripts/run-calibration.mjs --slices 4 --out .calibration/<name>` with the same `--env` levers. At most four slices and never two heavy runs at once: the machine crashed several times under six slices.
- Base reuse: `node scripts/run-calibration.mjs --reuse ...` prints the folder of a finished run under `.calibration/` whose fingerprint matches (git tree ids of the inputs at HEAD, content hash of `.smogon-cache` and `.fit-corpus`, lever env, Node version, slice count) and starts nothing; a dirty tree never reuses, `--dry-run` shows the decision without a run, and runs from before round 70 have no fingerprint.
- Quick tier: `--env EVAL_CALIBRATION_FRACTION=0.25` keeps a quarter of the universe (the same replays every time, each tranche and family in proportion) for about a quarter of the machine time; `paired-calibration.mjs` pairs a quick run against a full base on the shared rows and names the fraction and the pairing count in its header. A quick pair screens, and a resolved row can flip in the full pair, so gates read the full pair.
- Bank data in CI: the tarball holds `.smogon-cache` and every replay of `.fit-corpus` that the fit source and the holdouts read (`scripts/bank-data-pack.mjs`; since round 74 CI captures the fit corpus with search: `--env EVAL_CALIBRATION_SOURCE=fit --env EVAL_CALIBRATION_FAMILY=<family> --env EVAL_CALIBRATION_TURNS=thirds --env EVAL_CALIBRATION_FEATURES=1`); the tracked `test/regression/fixtures/bank-data.json` names its sha256 and folder hashes, and a CI job unpacks it only after both checks. When the data changes, pack again; the upload (`--upload`, a pre-release that is never Latest) waits for the user's okay.
- Crash protection (D23): commit before every heavy run and force freshly written files to disk; do not write to `.git` while the run is going. The repair recipe for zeroed `.git` files is in `docs/completed/` (incident of 20.09.2026).
- Worktrees: remove the junctions (`node_modules`, `.calibration`, `.smogon-cache`, `.fit-corpus`) one by one with `[System.IO.Directory]::Delete('<path>')` and check with a reparse-point scan before `git worktree remove`; otherwise git follows the junctions and deletes their targets (incident of 12.09.2026).
- A lane that moves dependencies gets its own `node_modules` (`npm ci` in the worktree; through a junction its install would rewrite MAIN's), and its Playwright runs start inside the worktree with their config there: a config under MAIN's `docs/` loads MAIN's `@playwright/test` beside the worktree's, and Playwright stops (round 87).
- File encoding: a PowerShell write without `-Encoding utf8` uses the ANSI code page (round 79: an em dash became the byte 0x97, and only the production build refused it); `test/regression/source-encoding.spec.ts` holds every source file to UTF-8.
- Line endings: the repository checks out with `core.autocrlf`. Scripts match `\r?\n`; count conflict markers before `git add`. Test logs stay LF through `.gitattributes`.
- Probes never go under `test/regression/` (the suite collects them); they are `.vt.ts` files under `docs/perf/probes/<date>/` with their own Vitest config and `PROBE_ROOT`.
- The replay iframe's own `Config` stub (`PS_CONFIG_DEFAULTS` in `src/lib/replay-html.ts`) must carry Showdown's routes: the client reads `Config.routes` while it loads, and its scripts load in no fixed order.
- Saved engine results (round 90): browser rows that judge a view (game-review except its Auto row, win-paths, lines-play) read results saved in `test/e2e/fixtures/eval-store/`; `EVAL_STORE=live` runs them live. A seeded page that starts a search fails the row and names `node scripts/capture-eval-store.mjs` (`--only <replay id or file name>`; 2 to 7 minutes per file on devbox). The helper rewrites the cache version, so a score-touching round needs no capture; a changed team build, record shape, game or turn list does. Live searches stay in eval, eval-graph, branch, play-out-finish, hard-mode, the Auto row and the win-paths job, singles and doubles.
- The dev server skips `.calibration`, `.claude`, `.fit-corpus`, `.playwright-mcp`, `.smogon-cache` and `docs` (`vite.config.ts`); a new local folder with many files goes into that list.
- Feedback runs use port 5176; an orphaned dev server there makes every run fail at once. Do not edit root Markdown files during feedback, e2e or bank runs (Vite reloads).
- `docs/` is local (gitignored) except `docs/completed/` and `docs/adr/`; issue texts that name `r<NN>/…` or `docs/perf/…` point to these local probe folders; `.claude/` is local except `.claude/agents/`. `deploy.ps1` and `FeedbackEval.xlsx` stay untracked.

## Change classes

Every change gets a class before work starts: the integrator proposes it, the user can move it. The class sets the process, so delivery stays fast and machine time goes where a measurement decides something.

| Class | What it is | Process | Measurement |
| --- | --- | --- | --- |
| Small fix | A bug or a small TODO with a known cause and a local fix: one function or a few files, no new weight, no re-fit, no change to the package API | Red test, fix, green, straight into the batch branch; no spec | None per fix; the batch check at the end |
| Larger bug | The cause is unclear or spans several modules, or the fix changes a rule many paths read | Diagnosis first (a probe with the scene and its numbers, written down), then its TODO issue, then the fix test-first | By its score class: lossless (D4) or score-touching (D3) |
| Feature | New behaviour for the user in the app, the engine or the package API | A round: brainstorming, spec with success criteria, plan, build with tests, measurement, user gate, booking | D3 or D4, as the change touches scores |
| Epic | A programme of several features (the Showdown Companion) | Its own spec and plan with ordered steps; each step runs as a feature round with its own gate | Per step |

- Small fixes collect in a batch on one branch, score-touching ones included. The batch ends with one check: the checks before push, the cache version bumped once, two feedback runs compared byte for byte with the tier census (round 70 ran one and missed a turn that varied from run to run), the paired bank only when the user asks for it. Every pin the batch moves waits for one gate at the end; each fix gets its own commit.
- A small fix that grows (a second cause, a re-fit, more than a few files) becomes a larger bug and gets its TODO.
- A feedback run takes about ten minutes and a bank run in CI about five (round 79), so a run per lane fits a wave and separates the lanes' effects; never one per fix.

## Working in rounds

- Rounds are numbered in one series across the project (the ledger calls them "improvement round N"). Each round: brainstorming and spec, build with tests, measurement, user gate, booking, push after the okay. A batch of small fixes is a round too: it gets a number and a short booking, without a spec and with its one check at the end.
- An audit or review that names a wrong rule leaves a TODO proposal with its red sweep the same day. A triage closes a TODO's issue only when the wrong rule is gone from the code; otherwise it parks the TODO with a trigger (round 70: four of the batch's 18 faults stood in the audit of 24.09., and the triage of 05.10. had closed one of them).
- Every TODO is a GitHub issue (user gate 07.11.2026). Its labels give its status (`approved`; `parked`, with its trigger in the text; `needs triage` for a report or a proposal), its class (`small fix`, `larger bug`, `feature`, `epic`), its score class (`lossless`, `score-touching`) and its area (`area: app`, `area: engine`, `area: replay-core`, `area: harness`); its milestone names the release. The board "PS Dashboard" gives each issue of a milestone its Status (Approved, In wave, Gate, Done) and, in a wave, its Lane. The TODOs from before 07.11.2026 keep their T-number in the title ("T344 · …"); a new one goes by its issue number. Pins in known drift carry the label `known drift`; library bugs for the user's upstream reports carry `upstream`.
- A new TODO needs the user's approval (user 21.10.2026). The gate that proposes it gives its user scene, what a user of the app or the packages sees, and whether it is worth building before the release; only an approved TODO gets the label `approved` and its milestone; a report from someone else stays at `needs triage` until a gate rules on it, and one the user turns down is parked with a trigger or closed.
- Booking at the end of a round: a ledger block in `test/regression/eval-calibration.spec.ts`, an entry in `docs/completed/<area>.md` (goal, delivered, evidence, measurement, gate, lessons, rests), the round's pull request, which closes its issues (`Closes #N`), and rests as TODO proposals for the gate and, once approved, as new issues with their labels and milestone. A fresh reviewer checks new TODOs against the code before their issues are written.
- Documentation moves with the change: a round updates the documents its change touches (README, GLOSSARY.md, ARCHITECTURE.md, ENGINES.md, EVALUATION.md, an ADR whose decision moves) in its own pull request, and the release pull request checks once more that they describe what ships (user 08.11.2026).
- The version moves with the release: the pull request of the wave or batch that closes the last open issue of a milestone raises the version itself (`npm version <minor|patch> --workspaces --include-workspace-root --no-git-tag-version`: the three manifests and the lockfile) and the release line under "The project", next to the docs check (user 22.11.2026, release 1.2.0; from 08.11.2026 a separate release pull request followed the merge). Its merge is the release, so it merges with the user's okay that names the release. A milestone that is no release (a clean-up) says so in its description and raises no version.
- Waves: several lanes in parallel, one branch and worktree per lane (its Lane on the board), no shared file, measurements through the integrator's queue (one heavy run at a time), the merge in a separate clone, then a wave run with all holdouts and one gate with a table over all lanes.
- Waves keep the documents current (user 14.11.2026): each lane brings the documents its change touches (README, GLOSSARY.md, ARCHITECTURE.md, ENGINES.md, EVALUATION.md, the ADR whose decision moves) on its own branch before its merge into the round's branch, and the lane's file list names them. The merge step checks that they are there, and the `wave-reviewer` reads the documents against the merged code before the final gate.

## Agents

- Roles in `.claude/agents/`: `wave-planner` (Opus, effort high, plans a step that needs judgment: a lane plan, a feature's stages, a diagnosis across modules; no commit), `wave-builder` (Sonnet, builds one step), `wave-reviewer` (Sonnet, checks claims against the code), `wave-scout` (Haiku, finds and counts), `wave-reader` (Haiku, reads measurements by the rules above), `wave-tester` (Opus, clicks through the running app in a browser and reports what works, what reads wrong and what looks off). The main session stays on Opus; of the sub-agents only `wave-planner` (user 05.11.2026) and `wave-tester` (user 12.11.2026) run on Opus, the others name Sonnet or Haiku in their frontmatter (`.claude/settings.local.json` lifts the global Opus setting).
- A UI plan ends with a `wave-tester` run on its built state, before its gate, and a wave ends with one on the merged head, before the final gate (user 12.11.2026). Its findings go to a builder or into the gate.
- One fresh agent per step, starting from the brief, the plan, the ledger and `git log`, and writing its step into the ledger before it stops. After a pause of more than five minutes do not resume an old agent. A monitor reports the end of a measurement, never a sleep.
