# Architecture

This document explains how the code works: the layers, how a replay becomes teams and a live simulator position, how the evaluation engine is built, and how the app and the test suites are organised. [EVALUATION.md](./EVALUATION.md) covers what the engine computes for the user, the measurement tools and the single list of known limits. [README.md](./README.md) covers setup and commands.

The code has three layers. `@fulllifegames/replay-core` turns a replay into teams and snapshots and has no network and no DOM. `@fulllifegames/eval-engine` rebuilds positions in `@pkmn/sim` and evaluates them. The app in `src/` holds the React UI, the worker glue and the caches. Lint zones in [`eslint.zones.mjs`](./eslint.zones.mjs) keep the layers apart, so the direction of imports is a build error, not a convention.

## Layers and packages

| Path | Role | May import |
| --- | --- | --- |
| [`packages/replay-core/`](./packages/replay-core/) | Protocol parser, opponent inference, spread solver, team builder, Smogon lookups | `@pkmn/*`, `@smogon/calc` |
| [`packages/eval-engine/`](./packages/eval-engine/) | Branch reconstruction, forward model, static evaluation, search, analysis | replay-core by name |
| [`src/`](./src/) | Components, hooks, workers, app libraries | both packages by name |

The zones enforce four rules. A package never reaches `src/` or the UI layer. replay-core never imports the engine. The app imports the packages by name and never their files. Inside the app, nothing under `src/lib` imports hooks, components, `App` or workers, and components use the facade hooks (`useBranch`, `useEvaluation`, `useAppController`) instead of their internals. Package tests import their own sources relatively and the sibling package by name.

Package names resolve to the package sources through a Vite alias ([`vite.config.ts`](./vite.config.ts)), the tsconfig `paths` and the Vitest alias, so dev, HMR, the build and the suites share one module graph and no test reads a `dist/`. `tsc -b` builds each package as a composite project with its own declarations. Package sources import each other with `.ts` specifiers and compile with `rewriteRelativeImportExtensions`, so the emitted JavaScript runs in Node without a bundler. Each barrel (`src/index.ts`) is curated and pinned by [`test/regression/package-api.spec.ts`](./test/regression/package-api.spec.ts).

The app loads heavy parts on demand: reconstruction, the forward model, choice locks, damage previews, serialization, the protocol parser, the opponent inferrer, the team builder and hidden-power go through the re-export modules in [`src/lib/lazy/`](./src/lib/lazy/). A barrel imported both statically and dynamically would fold into the entry chunk, so the facades keep the lazy boundary where it is, and `sideEffects: false` lets the bundler drop unused re-exports. The simulator and the dex data stay out of the entry chunk.

## Replay to teams

**Loading.** [`ReplayLoader.tsx`](./src/components/ReplayLoader.tsx) accepts a replay URL or id, a dropped or picked file (a "Download replay" `.html` export or a raw log), and an optional pasted team. [`useReplay`](./src/hooks/useReplay.ts) fetches `replay.pokemonshowdown.com/<id>.json` and falls back to the `.log` route when the JSON answer is refused, empty, not JSON or has no log ([`replay-fetcher.ts`](./src/lib/replay-fetcher.ts)). A private replay's `-{password}pw` suffix stays on the fetched id and is stripped from everything derived from it. File exports go through [`replay-file.ts`](./src/lib/replay-file.ts), which unwraps the log from the export's script and reads the id from the hidden `replayid` input, never from the file name. [`useEmbedHost`](./src/hooks/useEmbedHost.ts) adds the host routes: `?replay=`, `?embed=1` and the `ps-load-replay` message (the messages are in the README).

**Snapshots and observations.** `parseReplayLog` ([`protocol-parser.ts`](./packages/replay-core/src/protocol-parser.ts), with [`protocol/`](./packages/replay-core/src/protocol/)) feeds the protocol to `@pkmn/client` and records a `TurnSnapshot` at each turn boundary: both sides' Pokémon, field, side conditions and the protocol chunk. The snapshots drive the turn slider and correct reconstructed state later. The same pass collects damage observations from clean hits (no crit, no multi-hit, no `[from]` attribution, inside the current move action) with attacker, defender, move, boosts, screens, weather and the observed HP fraction. Speed-order observations (same-turn move order, KO before acting) feed the spread solver as speed constraints.

**Team precedence.** `buildTeamsFromReplay` ([`team-builder.ts`](./packages/replay-core/src/team-builder.ts), [`team/set-resolvers.ts`](./packages/replay-core/src/team/set-resolvers.ts)) fills each set from the first source that knows:

1. what the replay revealed, plus the user's manual edits
2. the pasted team for `p1` and Open Team Sheets
3. fitted spreads: the solver in [`spreads/`](./packages/replay-core/src/spreads/) checks legal EV-spread candidates against `@smogon/calc` roll ranges for every observation a Pokémon appears in, fits only the dimensions the evidence measures, and falls back to the prior when the best candidate misfits. Candidates are legalized to the format's budget before scoring: 508 total and 252 per stat, or 66 and 32 Stat Points in Pokémon Champions formats (detected from the `|tier|` line, [`ev-budget.ts`](./packages/replay-core/src/spreads/ev-budget.ts)). The solve runs in the replay worker, once per knowledge state, after the Smogon data settles.
4. Smogon usage guesses ([`src/lib/smogon-stats.ts`](./src/lib/smogon-stats.ts), [`src/lib/smogon/`](./src/lib/smogon/)): the `hosts.ts` fetcher tries data.pkmn.cc and then its GitHub Pages mirror, and formats without a stats file fall back to the generation's OU file. [`set-coherence.ts`](./packages/replay-core/src/set-coherence.ts) assembles guessed moves as a coherent published set scored against the revealed evidence, then applies pairwise vetoes. The stats panel ([`team-info.ts`](./packages/replay-core/src/team-info.ts)) and the simulator's team builder run the same selection, so the display never shows a set the engine would not play.
5. `@pkmn/smogon` set assumptions ([`src/lib/smogon-sets.ts`](./src/lib/smogon-sets.ts)) for the remaining gaps

**Stand-ins.** In a game without Team Preview a side whose log shows fewer bodies than its `|teamsize|` gets stand-ins for the rest, picked greedily from the format's teammate statistics ([`team/stand-ins.ts`](./packages/replay-core/src/team/stand-ins.ts), `withStandIns`). A pasted team fills the open slots of p1 first. A format whose Dex entry generates the team (Random Battles) has no statistics; its stand-ins come from the format's published random-set file instead (a draw seeded by the log's header, distinct base species, the file's level and one role's moves, ability and item), which the set fetch loads (`src/lib/random-sets.ts`).

**Rule-outs.** Protocol evidence removes candidates before a guess survives (`RevealedPokemonInfo.ruledOut`): hazard, status or weather damage disproves Magic Guard, rocks chip disproves Heavy-Duty Boots, a landed Ground move disproves Levitate, two distinct plain moves disprove every Choice item, a plain status move disproves Assault Vest, and a screen that ends after its plain five turns disproves Light Clay for its setter (after eight turns it proves it): `conditionTurns` ([`dex-facts/screen-turns.ts`](./packages/replay-core/src/dex-facts/screen-turns.ts)) gives the turns from the Dex condition, and [`inference/screen-evidence.ts`](./packages/replay-core/src/inference/screen-evidence.ts) reads the log's screen intervals. A logged effect that an ability would have refused rules that ability out, and a move's last PP spent with no berry line rules out a Leppa Berry. The first asks the simulator on a twin battle ([`sim-ask/effect-refusal.ts`](./packages/replay-core/src/sim-ask/effect-refusal.ts), [`inference/blocked-effects.ts`](./packages/replay-core/src/inference/blocked-effects.ts)), the second reads the Dex's own list of items that eat at 0 PP ([`inference/pp-trigger.ts`](./packages/replay-core/src/inference/pp-trigger.ts), `ppEaters` in `inference/item-triggers.ts`). A disproven ability or item walks to the next candidate, and a disproven Choice guess stops fabricating move locks.

**Bookings and the damage fit.** A move the log shows books to the body that used it: `bookingIdent` ([`inference/client-facts.ts`](./packages/replay-core/src/inference/client-facts.ts)) follows a body under Transform to the body it copied, and a Pledge combination or Round books the shown move. A knockout reads by the game's display bounds ([`hp-display.ts`](./packages/replay-core/src/hp-display.ts): percentage, 48-pixel bar or exact HP, with the Champions mod rounding down and Scarlet/Violet up), and `OBSERVATION_SLACK` lives in one module that the spread fit imports (`choice-lock.ts` keeps a deliberate copy, compared by `test/regression/observation-slack.spec.ts`). When no spread reaches a refuted knockout, [`spreads/item-rung.ts`](./packages/replay-core/src/spreads/item-rung.ts) offers the usage-listed boost items in turn. `PokemonSnapshot.ppUsed` carries the PP the log shows spent ([`protocol/parser-state.ts`](./packages/replay-core/src/protocol/parser-state.ts), from the client's counts).

Teams export to and import from Showdown text ([`src/lib/sets-io.ts`](./src/lib/sets-io.ts)); imports overlay as manual knowledge, persist per replay id and rebuild a live branch through the same refresh path as team edits. The team editor draws from legal pools in [`src/lib/pokemon-options.ts`](./src/lib/pokemon-options.ts), loaded on demand.

## Branch reconstruction

[`branch-engine.ts`](./packages/eval-engine/src/branch-engine.ts) is the facade over [`branch/`](./packages/eval-engine/src/branch/), and [`useBranch`](./src/hooks/useBranch.ts) wraps it in React state. `startBranch` builds a `@pkmn/sim` battle, orders both teams so the replay lead comes first, sends `default` for team preview, splits the protocol into turn blocks and replays the original choices up to the target turn. Doubles state is slot-indexed (actives, moves, targets, switch lists, forced-switch flags, pending choices); the single-active fields still point at slot 0.

- **Lockstep replay.** A block's choices are written only when the simulator stands at that block's turn. A simulator that ran ahead skips stale blocks, one that fell behind advances on defaults first, and a wedged battle stops. Taunt-blocked moves replay from their `|cant|` line. Synthetic logs (missing `|upkeep|`, CRLF) are tolerated.
- **Boundary corrections.** At the target turn the snapshot corrects HP, status and the active Pokémon, including bodies the simulator fainted that the real battle kept. Each pass restores the side invariants the simulator relies on (`pokemonLeft`, `isActive`) and reruns the disable pass and the request rebuild. Protocol `switch` and `drag` lines fix the active slots when simulator randomness would phaze a different target.
- **Choice locks.** [`choice-lock.ts`](./packages/eval-engine/src/choice-lock.ts) stamps the locks the protocol proves (one distinct committed move on an undisturbed Choice item since the last real entry; a guessed item also needs the damage record not to contradict it). Corrected actives enter without inherited locks, and the stamp lands before the request refresh.
- **Hax alignment.** The simulator draws its own dice, so a phantom crit or miss can contaminate a turn. `playBlock` in [`branch/runtime.ts`](./packages/eval-engine/src/branch/runtime.ts) plays each block with the dice the log names forced (`forcedTurnDice` in [`dice/logged-block.ts`](./packages/eval-engine/src/dice/logged-block.ts), read from the block by [`dice/logged-results.ts`](./packages/eval-engine/src/dice/logged-results.ts)). The dice the log hides come from index 0 of `ALIGNMENT_SEEDS` (`'1,2,3,4'`), reset every turn. `faintStep` plays the block on a copy first and scores the emitted events against the protocol block (game end and faint set first, then misses, crits, secondaries, hit counts, `|cant|` and move order, in [`hax-alignment.ts`](./packages/eval-engine/src/hax-alignment.ts)). A perfect score keeps the list. Otherwise `stepSets` tries the damage-roll steps of the hits on the bodies whose faint differs (the last step first, and it stops when that step misses a faint), and `seedSearch` plays seeds 1 to 15 of `ALIGNMENT_SEEDS` for the dice no `DieKind` names, with the forced list kept. `quietProcs` ([`dice/phantom-procs.ts`](./packages/eval-engine/src/dice/phantom-procs.ts)) forces every ability or item proc the log does not show to not happen. A turn the copy cannot play forced, or whose forced play would end a game the log goes on past, falls back to `alignBlockSeed`, the search over 16 pinned seeds ([`branch/arrival-dice.ts`](./packages/eval-engine/src/branch/arrival-dice.ts)). A turn that stays imperfect after the steps and the seed search keeps its forced result as a named residual. The arrival and the adopt (`alignArrivalDice`) run the same `faintStep`, so the first turn of a branch carries the dice of the rebuild. `AlignmentSummary` counts `seededTurns` and `fallbackTurns` beside the faint-residual turns. The pick is deterministic, and `ALIGNMENT_SEEDS` is a frozen literal: changing it is a cache-version event. Damage magnitude stays unscored because boundary snapshots already pin HP.
- **Faints and waits.** `takeBodyOut` ([`branch/team-order.ts`](./packages/eval-engine/src/branch/team-order.ts)) takes a body out the way the simulator's faint does: the End events of its ability and item, `faintQueued`, the fallen count. The snapshot correction, the replacement round's retire of the unshown bench and `faintThePredecessor` ([`branch/entry-effects.ts`](./packages/eval-engine/src/branch/entry-effects.ts)) all call it. `resolveForcedSwitches` waits for the simulator until either side holds a new request object, so a replacement that faints on entry to hazards asks for the next one without a timeout.
- **Turn-0 lead branch.** Target turn 0 rebuilds a fresh game to the start of turn 1 with the chosen leads first and no replayed blocks, corrections or locks. The lead decision is history entry 0 (`leadChoices`), and rebuilds of the variation re-seed it from that record.
- **Bring limits and worlds.** Bring-limited formats (VGC, BSS) run on a bring-all base format, so every reconstruction of such a replay trims the teams before the battle starts. `broughtSpeciesFor` ([`replay-format.ts`](./packages/replay-core/src/replay-format.ts)) reads the brought species from the log's `switch`, `drag` and `replace` lines, one per body, and `replayBringList` returns each side's fielded bodies with its weighted candidates for the bodies it never fielded. [`branch/bring-worlds.ts`](./packages/eval-engine/src/branch/bring-worlds.ts) turns the lists into at most three worlds (`BRING_WORLD_CAP`), each a set of guesses, and `blendWorlds` weighs the results of a full search per world by usage; `trimTeamsToBring` ([`branch/team-order.ts`](./packages/eval-engine/src/branch/team-order.ts)) holds "both sides or neither". The app keeps the serialized positions of the worlds in a registry ([`src/lib/eval/world-positions.ts`](./src/lib/eval/world-positions.ts)); `EvalWorkerClient.evaluate` runs a registered position once per world and returns the blend, and the bank does the same through `bankWorldsFor` in `test/regression/bank-build.ts` (ADR 0024).
- **Choices from the protocol.** The replayed choices follow the log through small modules of `branch/`: `relayed-move.ts` (a move line that Magic Bounce, Dancer, Magic Coat or Snatch wrote is no click), `action-bound.ts` and `cant-stand-in.ts` (the stand-in move and the order bound of a body that fell before it acted, from the simulator's queue place), `forced-choice.ts` with `forward/request-reviving.ts` (a revive line answers with the revived body, forced replacements fill the slots in the log's order), a stand-in click when the request would refuse a choice (`playableMove` in `protocol-choices.ts`), `sim-ask/hidden-aim.ts` (the aim of a failed move whose target the protocol hides, asked of the simulator on a copy) and `pp-restore.ts` (each move slot gets the PP the log shows spent).
- **New game.** A game starts from two pasted teams: `branch/new-game.ts` asks the simulator what the format's battle looks like at its start and what its team validation reports, and decides nothing; `branch/game-seed.ts` holds the default seed in a module of its own, so the start page carries no battle runtime. The record of the game (`NewGameRecord`, [`src/lib/new-game/record.ts`](./src/lib/new-game/record.ts)) is the truth: [`game-log.ts`](./src/lib/new-game/game-log.ts) makes the log as a pure function of it, [`store.ts`](./src/lib/new-game/store.ts) saves it (20 games at most) and [`hooks/branch/game-rebuild.ts`](./src/hooks/branch/game-rebuild.ts) plays it again from its seed through `replayHistoryEntry`, the road every variation rebuild takes.

**Position source and replay worker.** Heavy replay work runs in a dedicated replay worker, a second instance of the worker script ([`client.ts`](./src/lib/replay-jobs/client.ts) with a job queue and abort-by-termination, [`handlers.ts`](./src/lib/replay-jobs/handlers.ts)), separate from the evaluation pool so cancelling an evaluation never kills a reconstruction. `startBranch` takes its runtime from the app's one position source ([`usePositionSource.ts`](./src/hooks/usePositionSource.ts)). The source answers from the exact-position store (a session cache keyed by replay, turn and sets) or asks the worker, which streams every healed boundary into the store. The arrival becomes the live runtime through `adoptSerializedRuntime` ([`branch/adopt.ts`](./packages/eval-engine/src/branch/adopt.ts)). Only a simulator that cannot start falls back to main-thread reconstruction. Evaluate, the dwell rebuild and the sweep share this source, so a position is reconstructed once per knowledge state.

**The copy with the die turned over.** The report names the die it calls the game's biggest roll with both chances, and the second one needs a position the game never reached: the logged turn with that one die turned over. `rolledCopy` ([`branch/rolled-copy.ts`](./packages/eval-engine/src/branch/rolled-copy.ts)) plays it on a fork of the boundary position with the rebuild's dice and the faint step, and the replay worker answers it as the job `rolledCopy` ([`handlers.ts`](./src/lib/replay-jobs/handlers.ts)). The last stage of the sweep ([`sweep-rolled.ts`](./src/hooks/evaluation/sweep-rolled.ts), [`rolled-copy-stage.ts`](./src/lib/rolled-copy-stage.ts)) evaluates the copy once per replay through `EvalWorkerClient.evaluate`, with no new engine protocol message, and `computeGameReportData` hands the result to `buildGameReport` ([`biggest-roll.ts`](./packages/eval-engine/src/biggest-roll.ts) writes the sentence).

## Evaluation engine

The engine lives in [`packages/eval-engine/src/`](./packages/eval-engine/src/) in five layers. The sim work stays off the main thread, and everything above it is pure and unit-testable.

1. **Forward model** ([`forward-model.ts`](./packages/eval-engine/src/forward-model.ts), [`forward/`](./packages/eval-engine/src/forward/)). It forks the serialized battle, enumerates legal choices (singles and combined doubles choices with targets, one Tera, Mega or Ultra Burst per side per turn, a `wait` sentinel for a side waiting out a forced switch), advances joint choice pairs under fixed seeds and resolves follow-up forced switches. Deserialization passes a repair layer. [`scripted-prng.ts`](./packages/eval-engine/src/forward/scripted-prng.ts) lets a caller script the accuracy, crit, damage roll and secondary dice of one move. The dice module ([`dice/`](./packages/eval-engine/src/dice/)) names every die of a turn by the simulator's own hook (`recognize`, `watchBattle`, ADR 0002), in 16 kinds since round 89 (a die per later hit of a multi-accuracy move, the random target and the drag among them; [`dice/chain.ts`](./packages/eval-engine/src/dice/chain.ts), [`dice/logged-picks.ts`](./packages/eval-engine/src/dice/logged-picks.ts)). It also plays a turn with every die at its likeliest result ([`dice/likeliest.ts`](./packages/eval-engine/src/dice/likeliest.ts)) and records a turn's chance dice to play each one the other way ([`dice/flip.ts`](./packages/eval-engine/src/dice/flip.ts)), and it serves three callers: the branch's forced dice, the rebuild's logged dice and the search's scripts, which ask a `DrawNamer` ([`dice/namer.ts`](./packages/eval-engine/src/dice/namer.ts)) for each draw instead of reading the numbers of the call. The simulator speed layer in [`forward/sim-fast/`](./packages/eval-engine/src/forward/sim-fast/) (clone plan, handler dispatch, guard, rule table) makes forks cheap; the `EVAL_SIM_FAST` variable switches it (`0` off, `1` all levers, or a list of `rules`, `clone`, `dispatch`), and CI runs the engine suite with it off and on. Pokémon Champions battles run on the Champions mod of `@pkmn/mods`, which [`sim-mods.ts`](./packages/eval-engine/src/forward/sim-mods.ts) loads on demand for a Champions format only.
2. **Static evaluation** ([`eval-function.ts`](./packages/eval-engine/src/eval-function.ts), [`score/`](./packages/eval-engine/src/score/)). A fittable feature vector (bodies, HP, status, boosts, hazards, screens, speed control, an aggregated 1v1 matchup term with finite heal races, entry costs and stranded bench pieces, among others) times a weight table. `featureWeights(doubles, ruleset)` in [`score/weights.ts`](./packages/eval-engine/src/score/weights.ts) picks one of five tables: singles, Doubles OU, VGC doubles, Champions singles and Champions doubles. The `EVAL_FIT=1` harness fits them on the manifest-pinned corpus (about 5,600 games) with cluster-bootstrap errors, and a table changes only through the calibration gate. A phase-aware logistic maps scores to win probability once, at the search leaf ([`winprob.ts`](./packages/eval-engine/src/winprob.ts)), and `DISPLAY_K` is the second stage the displayed percentage passes through.
3. **Search** ([`search.ts`](./packages/eval-engine/src/search.ts), [`search/`](./packages/eval-engine/src/search/), [`mcts.ts`](./packages/eval-engine/src/mcts.ts), [`rank.ts`](./packages/eval-engine/src/rank.ts)). The matrix mode evaluates the joint choice matrix with iterative deepening and prunes dominated rows and columns, then solves it as a matrix game by regret matching. The tree mode runs DUCT Monte-Carlo trees (four trees; each answers the named dice of a root cell by a quantile of its own, [`search/root-quantile.ts`](./packages/eval-engine/src/search/root-quantile.ts), and draws below the root from seeds hashed from tree and iteration, `treeSeed` in [`search/leaf.ts`](./packages/eval-engine/src/search/leaf.ts); the tree holds no chance nodes, ADR 0023; [`mcts-merge.ts`](./packages/eval-engine/src/mcts-merge.ts) pools each outcome class of a root cell across the trees that drew it) and ranks the root with the same equilibrium solve. The matrix, the verify round, the pair search and the trend probe read each cell's own seed list (`cellSeed`). [`verify-select.ts`](./packages/eval-engine/src/verify-select.ts) picks the cells that the matrix-grade sampler re-prices before the solve. Boundary cells, where a priceable accuracy, KO-range damage roll or secondary effect decides the outcome, are priced as mixtures of outcome classes ([`ko-odds.ts`](./packages/eval-engine/src/ko-odds.ts), [`cell-blend.ts`](./packages/eval-engine/src/cell-blend.ts), [`pair/`](./packages/eval-engine/src/pair/), [`search/secondary-classes.ts`](./packages/eval-engine/src/search/secondary-classes.ts) for their keys, and [`dice/secondaries.ts`](./packages/eval-engine/src/dice/secondaries.ts) for the chances the simulator gives). The Auto mode is a spec resolved per turn before dispatch from `SEARCH_BUDGET_DEFAULT` in [`search/budget.ts`](./packages/eval-engine/src/search/budget.ts): doubles run the tree from the first turn, singles run a depth-1 matrix until a quarter of the bodies have fainted (`AUTO_MCTS_FAINTED_FRACTION`) and the tree after that. Stored results carry the concrete engine that ran. The single builder from simulator bodies to `@smogon/calc` Pokémon lives in [`calc/`](./packages/eval-engine/src/calc/); the forced-win prover and the endgame solver are in [`endgame/`](./packages/eval-engine/src/endgame/) and [`search/forced-win.ts`](./packages/eval-engine/src/search/forced-win.ts). The solver's `oneTurnMatrix` (every option pair played once, each child at its static value) is a production path since round 89: the win-path search ([`endgame/win-paths/`](./packages/eval-engine/src/endgame/win-paths/)) takes the engine's first choice at each position from it. That module holds the three steps of a lost endgame (a stronger play from the prover's plan, the likeliest lucky dice, the smallest mistake by the opponent), each under its own counted budget (`WIN_BUDGET`), and runs only as an on-request job. The hit cost and the end of the turn are memoized per board: [`score/board-key.ts`](./packages/eval-engine/src/score/board-key.ts) keys the state a play reads, and the fields come from the Dex at run time (the handlers' source, scanned by [`dex-facts/state-readers.ts`](./packages/eval-engine/src/dex-facts/state-readers.ts) and `handler-source.ts`), so a new simulator version needs no list of ours.
4. **Orchestration** ([`orchestrator.ts`](./packages/eval-engine/src/orchestrator.ts), [`tree-orchestrator.ts`](./packages/eval-engine/src/tree-orchestrator.ts), [`worker-client.ts`](./src/lib/eval/worker-client.ts), [`eval-worker.ts`](./src/workers/eval-worker.ts)). A pure async orchestrator, with exact parity to the sync search, fans work out over a worker pool sized to the machine ([`pool-size.ts`](./src/lib/eval/pool-size.ts)). Workers post progress far faster than a panel can render, so [`throttle-latest.ts`](./src/lib/eval/throttle-latest.ts) collapses progress and partial results to the latest value per interval. After the prover, the tree orchestrator runs the lines job (`withLines` in `tree-orchestrator.ts`): the executor's optional `lines` method replays the line of each requested row on a battle ([`search/lines.ts`](./packages/eval-engine/src/search/lines.ts), the donor trees chosen by [`search/line-donors.ts`](./packages/eval-engine/src/search/line-donors.ts)), the worker answers a `lines` message with `linesResult`, and the result gains the optional `EvalResult.lines`. A failed job leaves the result as it was, and an executor without the method (a mock, an external engine) sends none. The on-request job ([`on-request.ts`](./packages/eval-engine/src/on-request.ts), `runOnRequestJob`) is the second kind of work a worker does outside a sweep: a `job` message names its kind (today `winPaths`), the worker streams a `jobStep` for each step and ends with a `jobResult`, and the app's [`OnRequestJobs`](./src/lib/eval/on-request-jobs.ts) gives each job a worker of its own, outside the pool, so a sweep never waits for it and ending it never touches a sweep. [`useWinPaths`](./src/hooks/useWinPaths.ts) is its only caller; no job writes into an `EvalResult`, and the worker messages are internal, so `ENGINE_PROTOCOL` keeps its value. Workers build as ES modules (`worker.format: 'es'`), and the replay-job handlers load as their own chunk so the pool's script stays small.
5. **Analysis** ([`played.ts`](./packages/eval-engine/src/played.ts), [`analysis.ts`](./packages/eval-engine/src/analysis.ts), [`turn-analysis/`](./packages/eval-engine/src/turn-analysis/), [`leads.ts`](./packages/eval-engine/src/leads.ts), [`opponent-model.ts`](./packages/eval-engine/src/opponent-model.ts), [`sensitivity.ts`](./packages/eval-engine/src/sensitivity.ts), [`summary.ts`](./packages/eval-engine/src/summary.ts), [`report.ts`](./packages/eval-engine/src/report.ts)). It reads the played actions from the protocol, matches them into the ranked lists, splits each swing into a decision part and a chance part, grades regret in win-probability units, and adds the verification, sacrifice, sensitivity and Read passes before the prose layer speaks. Narrative-only signals (streaks, decided-sweep stages, odds quotes) are computed at render time and never change a grade. [EVALUATION.md](./EVALUATION.md) describes the behaviour.

**Engine protocol** ([`engine-api/`](./packages/eval-engine/src/engine-api/)). Another engine answers `ps-dashboard-engine/1` over HTTP ([ENGINES.md](./ENGINES.md)). `buildEngineRequest` turns a serialized position and the options the dashboard ranks into a request (the spectator log, each side's request JSON, the full state), `validateEngineResponse` holds an answer to the protocol, and `engineResponseToResult` reads it through the ranking the own search uses (`rankFromMatrix`, `toResult`) when the answer carries a matrix. `checkEngine` runs the same checks against an endpoint for `npx @fulllifegames/eval-engine check-engine <url>` ([`bin/eval-engine.mjs`](./packages/eval-engine/bin/eval-engine.mjs), with the sample positions in [`samples/`](./packages/eval-engine/samples/)).

## App structure

[`App.tsx`](./src/App.tsx) composes the output of [`useAppController`](./src/hooks/useAppController.ts), which stacks four hooks in [`src/hooks/controller/`](./src/hooks/controller/) with explicit inputs: the replay context, the transient interaction state, the board (timeline pointer, deviation and rebuild, branch refresh) and the engine (position acquisition, evaluation view, the engine walk, the play-out loop).

**Unified timeline.** The replay is the main line, at most one variation exists, and a position pointer (`viewTurn` + `viewLine`) replaces any mode split. [`src/lib/timeline.ts`](./src/lib/timeline.ts) holds the pure model: position "turn T" means the state before turn T, and a deviation classifies as open, extend, truncate or replace. The chosen line is sticky until an explicit main-line click. `PSReplayFrame` shows the original replay for main-line positions and the branch log for variation positions; navigation sends one-shot seek requests, and a seek-intent guard stops a freshly remounted frame from knocking the chosen turn back with its boot echoes. `BranchPanel` renders at every position from the best available source: the live simulator at the variation tip, a recorded serialized position elsewhere in the variation, or snapshot plus guessed teams on main-line turns whose exact position is not yet known (upgraded in place once the position source delivers it). Every deviation funnels through one path: chess rules, then the proven rebuild, then the move.

**Replay frame.** The viewer iframe loads a generated blob document with `replay-embed.js` from play.pokemonshowdown.com. The iframe has no `sandbox` attribute: a same-origin blob document with `allow-scripts` can strip its own sandboxing, so the attribute bought console noise and no isolation. The app depends on Showdown-hosted scripts and sprites at run time and is not self-contained. On narrow screens the embed keeps its desktop layout inside a horizontally scrollable container with a 640 px minimum width.

**Evaluation hook and sweep.** [`useEvaluation.ts`](./src/hooks/useEvaluation.ts) drives [`src/hooks/evaluation/`](./src/hooks/evaluation/): preferences, the single-position path and the three-pass graph sweep (a depth-1 scan, then the configured settings on every report-worthy swing, then every remaining turn). Single results are tagged with the position they started at, so a run that finishes after the user navigated away renders as stale. Every position, in the sweep and in a single evaluation, comes from the boundary-corrected reconstruction through the position source. The sweep waits for the Smogon fetches so it never bakes teams without the guessed fills. Graph writes are monotone (`supersedesStored`): a shallower pass never overwrites a deeper stored turn, and across engines the configured engine decides.

**Eval cache and its version rule.** Results are cached in memory and in IndexedDB ([`src/lib/eval-cache-store.ts`](./src/lib/eval-cache-store.ts)). A key reads `v<N>|<cacheKey>|d<depth>s<samples>m<mode>t<tera>`, where the cache key carries the replay, turn and a sets fingerprint; a non-default search budget adds a tag to the version. `EVAL_ENGINE_CACHE_VERSION` in that file must be bumped in the same commit as any change to what a position evaluates to (rules, weights, search, reconstruction), so a stale result is never read as current.

**Lines and the Game review.** [`LinesSection.tsx`](./src/components/eval/LinesSection.tsx) mounts under a turn's analysis and reads `graph.results[turn - 1].lines` through the pure view model in [`src/lib/line-view.ts`](./src/lib/line-view.ts) (`lineBlocks`, the words of every die kind). `usePlayLine` turns a line into a variation ([`src/lib/line-history.ts`](./src/lib/line-history.ts) writes one history entry per step, the dice riding on the slot choices) through the saved-variation restore. [`game-review.ts`](./src/components/eval/game-review.ts) holds the one rule for which turns the Game review lists and the graph marks, and `GameReviewPanel.tsx` shows them.

**Games in the app.** [`useNewGame`](./src/hooks/useNewGame.ts) promotes a turn played at the game's tip into the main line (the record takes its entries and lines, the exact store the position, the replay state the grown log); [`useGameReplay`](./src/hooks/useGameReplay.ts) and [`useGamePositions`](./src/hooks/useGamePositions.ts) serve the game's replay data and positions from the record, so no `replay` job runs; [`useGameTeamEdit`](./src/hooks/useGameTeamEdit.ts) plays the record again on edited teams and asks before it cuts played turns. The `Game` menu ([`LoaderMenu.tsx`](./src/components/LoaderMenu.tsx), [`GameEntry.tsx`](./src/components/GameEntry.tsx)) holds the replay loader, `New game` ([`NewGameDialog.tsx`](./src/components/NewGameDialog.tsx), loaded on first use so the start load holds no simulator code) and the saved games ([`SavedGamesList.tsx`](./src/components/SavedGamesList.tsx)). [`useOpenAddress`](./src/hooks/useOpenAddress.ts) writes `?game=<id>` or `?replay=<id>` with `replaceState` and reads it once at start. The share link of a game (version 2, [`src/lib/new-game/share.ts`](./src/lib/new-game/share.ts)) is read by [`hooks/branch/share-open.ts`](./src/hooks/branch/share-open.ts), which starts the format's battle on the seed and plays the entries; the state file keeps version 1 with the optional `game` (ADR 0014).

Other app modules: `BranchSaveSharePanel` saves compact branch reports locally and builds URL-hash share payloads (a replay's carry its identity, branch choices and final log, a game's the teams, seed and entries); [`src/styles/`](./src/styles/) holds the stylesheet in domain files, audited for dead classes by `test/regression/css-audit.spec.ts`.

## Testing and build

[`vitest.config.ts`](./vitest.config.ts) defines four projects. `app` runs [`test/regression/`](./test/regression/) (app specs, integration specs, the API snapshot and the measurement chains). `replay-core` and `eval-engine` run each package's `test/` folder, white-box against `../src` (`npm test -w packages/<name>`). `ui` runs [`test/ui/`](./test/ui/), one spec per component and hook under jsdom with Testing Library (`npm run test:ui`). Root specs consume the packages by name over the barrels; only the calibration, fit, endgame-truth and speed-layer-setting specs read package internals. The browser suites stay on Playwright: [`test/e2e/`](./test/e2e/) (one file per theme), [`test/e2e-build/`](./test/e2e-build/) (production build smoke) and [`test/e2e-feedback/`](./test/e2e-feedback/) (on demand, `npm run test:feedback`: pinned and census replays swept through the real app, graded warn-only against expert truths, with the report written to `docs/reports/`, which stays local and untracked).

The measurement harnesses live in `test/regression/` and [`scripts/`](./scripts/): the calibration bank (`eval-calibration.spec.ts`, `bank-*.ts`, `run-calibration.mjs`, `paired-calibration.mjs`), the fit (`eval-fit.spec.ts`, `build-fit-corpus.mjs`), endgame truth (`endgame-truth.spec.ts`) and the engine bench (`packages/eval-engine/test/eval-bench.spec.ts`). EVALUATION.md lists their commands and environment variables.

[`.github/workflows/test.yml`](./.github/workflows/test.yml) has six jobs: the Node suites, the eval-engine project under `EVAL_SIM_FAST=0` and `=1`, the dice sweeps over every move of the Dex (`DICE_SWEEPS=full`), the browser flows and the production build smoke, which also runs `npm run pack:smoke`. The workflow takes `workflow_dispatch`, so a pushed branch can run all six. `npm run pack:smoke` packs both packages, installs the tarballs into a throwaway project, runs the worked examples and type-checks a NodeNext consumer. `scripts/publish-packages.mjs` publishes the changed packages from `release.yml`. The `.github/workflows/pages.yml` workflow hosts the release channels.
